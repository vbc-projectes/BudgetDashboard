## Commands

```bash
# Electron desktop app (development)
npm start

# Web/server mode (Express on port 3000)
npm run start:web

# Run all tests
npm test

# Run a single test file
npx jest tests/dashboardService.test.js

# Run tests with coverage
npx jest --coverage

# Build distributables (Windows NSIS, Linux AppImage/deb, macOS DMG)
npm run dist

# Bump version in package.json
node scriptVersion.js
```

Tests use an in-memory SQLite database (`DB_PATH=:memory:` set in `tests/jest.setup.js`). No real DB or network access is needed to run the suite.

## Dual deployment model

The app ships as **two runtimes from one codebase**:

| Mode | Entry | Transport |
|------|-------|-----------|
| Electron desktop | `main.js` | IPC via `preload.js` context bridge |
| Web / Docker | `server.js` | HTTP (Express) |

`public/js/apiConfig.js` is the frontend adapter that makes this transparent: it detects `window.electronAPI` and routes calls through IPC; otherwise it falls through to native `fetch`. Every frontend API call goes through `window.fetch` (overridden by apiConfig) so no frontend code knows which runtime it is on.

The same **service layer** (`src/services/`) is called by both `src/ipc/ipcHandlers.js` (Electron) and `src/routes/` (web). Never duplicate logic between them.

## Architecture layers

```
public/                    ← Frontend (vanilla JS, no framework)
  index.html               ← Single HTML page; all tabs loaded lazily
  js/apiConfig.js          ← IPC↔fetch adapter (load order critical)
  js/TransactionManager.js ← CRUD base class for gastos/ingresos/impuestos tabs
  Pestañas/{tab}/          ← Per-tab HTML + JS entry point
  js/tabModules/{tab}/     ← Modular logic split from the tab entry point

src/
  config/
    database.js            ← SQLite Proxy; switch DB path with db.__setDbPath()
    userManager.js         ← Per-user folder structure under usuarios/
    config.js              ← All env vars with defaults
  routes/
    index.js               ← Mounts all sub-routers
    routeFactory.js        ← Generates /add/, /update/, /delete/ CRUD routes
    {domain}.js            ← Hand-crafted routes for complex domains
  services/
    BaseService.js         ← Abstract CRUD (getAll, add, update, delete)
    PuntualService.js      ← Extends Base for one-time transactions (fecha field)
    MensualService.js      ← Extends Base for recurring transactions (desde/hasta)
    dashboardService.js    ← All aggregation queries; has 1-min resumen cache
    yahooFinanceService.js ← Yahoo Finance + stooq fallback; tiered in-memory cache
  migrations/              ← Numbered sequential files; auto-run on startup
  ipc/ipcHandlers.js       ← Registers all Electron IPC channels
  database/migrationRunner.js ← Discovers and applies pending migrations
```

## Database

- SQLite per user at `usuarios/{username}/finanzas/finanzas.db`
- The `db` export from `src/config/database.js` is a **Proxy** that forwards to the currently active connection. Switching users calls `db.__setDbPath(newPath)` which closes and reopens the connection.
- `PRAGMA foreign_keys = ON` is set on every connection open.
- Migrations run automatically on startup (and on user switch in Electron). To add a migration, create `src/migrations/{next_number}_{name}.js` exporting `async function up(db, dbRun)`.

## Route conventions

Routes generated by `routeFactory.js` follow this pattern:
- `POST /add/{entity}_puntual` — create one-time record
- `POST /add/{entity}_mensual` — create recurring record
- `POST /update/{entity}_puntual` / `_mensual` — update
- `POST /delete/{entity}_puntual` / `_mensual` — delete
- `GET /dashboard` — all table data for the current user (used by TransactionManager)
- `GET /resumen-periodos` — aggregated KPIs for 1m/3m/6m/1y/5y/10y (cached 1 min)

Domain-specific routes live in `src/routes/{domain}.js` and are mounted at `/`.

## Key data model conventions

- **Puntual** transactions have a `fecha` (`YYYY-MM-DD`).
- **Mensual** recurring transactions have `desde` and `hasta` (`YYYY-MM`). The string `"9999-12"` means open-ended.
- `ingresos_*` tables have a nullable `bruto` column. When `bruto IS NOT NULL AND bruto != monto`, the difference is treated as income tax withheld.
- `gastos_mensuales` has `ipc_porcentaje` for inflation adjustment. Use `calcularMontoIpc()` from `src/utils/calculations.js` to evaluate the effective monthly amount.
- All monetary amounts are stored as `REAL` in EUR (or the asset's native currency for bolsa).

## Frontend script load order

The order of `<script>` tags in `public/index.html` is load-order–sensitive:
1. Translation files (`idiomas/*.js`) → `idiomas/idiomas.js`
2. Theme system (`Temas/temas.js`)
3. **`js/apiConfig.js`** — must load before any code that calls `fetch`
4. `js/customModal.js`, `js/TransactionManager.js`
5. Tab modules (`Pestañas/*/`, `js/tabModules/*/`)
6. Main modules (`js/main/`)
7. `main.js` last

## Multi-user pattern

Each user is completely isolated: separate SQLite file, separate upload folder. In **Electron** the active user is tracked in memory (`ipcHandlers.js`) and persisted to `usuarios/.current_user.json`. In **web** mode, the server starts with the last-used user and only one user is active at a time (single-process).

## Yahoo Finance / external data

`src/services/yahooFinanceService.js` maintains in-memory caches:
- Current prices: 5-minute TTL
- Historical data: 30-minute TTL
- FX rates (EUR conversion): 1-hour TTL

It falls back to stooq when Yahoo Finance is blocked. Non-EUR prices are converted to EUR on every read. The cache is process-scoped — a server restart clears it.

## Testing notes

- All tests set `DB_PATH=:memory:` so they run against a fresh in-memory DB.
- `tests/jest.setup.js` is the only setup file; it sets environment variables before any module loads.
- Tests import service classes directly; no HTTP server is started.
- The `yahooFinanceService` tests mock network calls — check existing mocks before adding new ones.
